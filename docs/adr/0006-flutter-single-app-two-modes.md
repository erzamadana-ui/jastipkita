# ADR 0006 — One Flutter app with buyer and traveler modes

- Status: Accepted (2026-09)
- Deciders: owner (GM), engineering

## Context
Many users are both penitip (buyer) and traveler (a jastiper who also buys from others). Two store apps would double
review, release and account-deletion obligations, and split trust signals of one person across two installs.

## Decision
- One Flutter codebase (`apps/mobile`) for Android, iOS and web (`/jastipkita/app/`), one account, with a mode
  switch (`users.active_mode` via `POST /v1/me/mode`). Traveler features are gated by KYC level (≥ 3 to accept,
  4 to publish verified trips).
- Design tokens generated from `packages/design-tokens` (`lib/core/design/tokens.g.dart`); API base URL and other
  public settings via `--dart-define` (`apps/mobile/dart_defines.example.json`); no secrets in the binary.
- Platform folders are generated by CI (`flutter create`) until committed; the artifact `mobile-platform-scaffold`
  lets the mobile engineer commit them.

## Consequences
- One store listing, one data-safety form, one account-deletion path (in-app + web URL).
- Store reviewers see financial features (SafePay) → organization developer accounts recommended
  (`docs/checklists/store-checklist.md`).
- The mode switch must never leak one role's data to the other; the API enforces roles per transaction, not per mode.

## Alternatives considered
- Separate traveler app — clearer UX for pros, but double compliance cost; revisit if travelers become a distinct
  professional segment.
